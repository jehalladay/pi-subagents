# 12 — Trust model, authorization, isolation and sensitive data

## Threat categories

1. Trusted developer-authored workflow scripts with access to selected local capabilities.
2. Scripts generated by LLMs and reviewed or executed under explicit policy (not inherently trusted).
3. External scripts/package dependencies (untrusted unless separately isolated).
4. Native SDKs with privileged credentials, potentially able to modify workspace, resources and remote state.
5. Tool outputs, repository code, agent messages and observations containing prompt-injection content or secrets.
6. Cross-workspace/tenant observer attempting to read/cancel another execution.

## The VM is not a security boundary

src/workflow/worker-source.ts documents host-function constructor escape concerns. node:vm with codeGeneration disabled is helpful for API discipline/determinism but not a robust hostile-JavaScript isolation boundary. **Never inject privileged objects or secrets into this VM.** For untrusted scripts use a separate restricted process/container with OS-level filesystem/network policy and mediated RPC, or refuse to execute. Worker threads alone do not give OS process isolation.

## Authorization design

- Caller identity and scope bound at workbench entry point; impersonation from script payload prohibited.
- Separate discover, inspect, observe, invoke and control grants.
- Node cap must be explicitly allowed in workflow and Claude agent role; never auto-share all registered providers.
- Policy enforced in privileged host *after* receiving RPC, not only by hiding tool names.
- Control decisions require native ownership/preconditions and, for destructive actions, operator confirmation.
- Treat unknown permission data as deny.
- Source/deployment pin must be checked before loading; malformed schema/unsupported contract fails closed.

## Credential boundaries

Pi operator host/deployment owns credential sourcing; providers borrow secure SDK clients; no serialized clients/private tokens across worker channel. Agent tools use scoped capabilities and API-specific credentials as supported. Disable untrusted script filesystem/network; redact tokens from logs, UI, recordings and failure messages.

## Input and output hardening

Bound recursively nested JSON, bytes, array length, call count, response size and event rate. Prevent prototype pollution and weird structured-clone prototypes at RPC boundaries. Validate Unicode and terminal escape sequences before display (no untrusted ANSI injection). Inspect evidence through authenticated adapters, not arbitrary shell file reads. Treat observed tool outputs as data, not instructions for Pi designer.

## Supply chain

Keep upstream MIT notices and original fork history. Pin SDK versions, package/artifact digests and provenance. Forge builds/reproducibility are authoritative. Avoid unrestricted dynamic plugin loading from arbitrary paths; provider packages require an allowlisted manifest/version/digest.

## Worktree and concurrency safety

Agent isolation "worktree" must be honored strictly; failure to isolate refuses start, not runs in shared cwd. Distinct agent workspaces must not accidentally share writable package state even if Forge caches immutable data. Build gate on exact candidate basis. Cancellation/cleanup must not delete a shared child workspace without ownership.

## Auditability

Record authorized principal, capability contract version, logical invocation, target native ref, reason/policy, request acknowledgment and producer outcome for control operations. Keep sensitive payload refs separate and access-controlled. Logs are not a source of entitlement.

## Security acceptance tests

Host-side deny even when script crafts raw RPC; JS VM escape attempt must not yield privileged provider client in declared isolation mode; unknown/expired grant refused; observer-only stop refused; cross-workspace ref returns authorization failure; ANSI escape output sanitized; secret env not displayed; schema pollution payload refused; isolated agent cannot see host tools not explicitly granted.
