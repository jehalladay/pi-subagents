- EAT-R073. `runWorkflow` refuses a `concurrency`, `agentCap`, `itemCap` or `nestedCap` that is not a positive safe integer (`Number.isSafeInteger`, at least 1). The refusal is a `WorkflowRuntimeError` ("Workflow <name> must be a positive integer."), raised before anything is dispatched. Before this cut, 0, -1 and NaN parked every agent behind a semaphore with no permits, so the run hung, and 0.5 and Infinity were accepted. Every positive safe integer is accepted, 2^31 and `Number.MAX_SAFE_INTEGER` included, and 2^53 is refused. An unset limit keeps its default: the concurrency `workflowConcurrency()`, clamped to [1, 16], and the caps `WORKFLOW_AGENT_CAP` (1000 agents), `WORKFLOW_ITEM_CAP` (4096 items; the suite reaches it through `parallel()`) and `WORKFLOW_NESTED_CAP` (256 nested `workflow()` calls). `HostAdmission` refuses each of its four limits the same way (`HostAdmissionError`, code `invalid-limit`, naming the limit): a pool limit may be any positive safe integer, and the queue deadline stops at setTimeout's ceiling of 2147483647 ms.
- EAT-R074. A host builds one `HostAdmission` and hands it to every run it starts (`RunWorkflowOptions.hostAdmission`). It holds three pools with separately configured limits: `sdk-queries`, `child-processes` and `forge-operations`. `dispatchPools` states the charge. An agent dispatch is an owned SDK query and a host child. A live node dispatch is a host child, and a `forge.*` node is also a Forge operation. A call replayed from the resume journal is not a dispatch and takes no slot. A run takes its own permit first (for an agent its concurrency, for a node one of its 16 node permits) and the pools last, before the dispatch. The budget is a counter and a first-in-first-out line per pool, not a second scheduler: it never orders runs against each other, never prioritises, retries or starts work. Pools are always taken one at a time in the same order, whatever order a request names them in, so two requests never wait on each other in a cycle, and a pool named twice is taken once.
- EAT-R075. A request that has to queue is told why through `onQueued`, once per pool it queues on and at the moment it queues there, and never for a pool that admits it at once: the pool, its limit and load, and the line ahead. A report that throws strands nothing. `RunWorkflowOptions.onAdmissionWait` adds the call's kind and the position its progress row carries. `HostAdmission.waiting()` lists every queued request under the pool it waits on, with the line ahead of it and its measured wait (monotonic, `performance.now()`), in counts and pool names only. A lease carries the monotonic wait from its request to its admission. The queue deadline bounds the whole wait of one request, across every pool it names: past it the request is refused, typed (`admission-deadline`, naming the pool), hands back every pool it had taken and leaves the line. The run then fails, as the agent cap fails it. An agent refusal is a fatal error and goes on record as an attempt that did not settle. A node refusal carries an `unavailable` CapabilityError diagnostic and leaves an error row; nothing new goes on record, and an override's original effect row is carried forward. Nothing is dispatched.
- EAT-R076. The run's end, by abort or by failure, takes every queued wait of that run out of the line by the time the run settles, and a skip takes its agent's wait out at once. The request hands back every pool it had taken, is counted in `cancelledWhileQueued` and is never dispatched; a skipped agent also hands back the run's own permit. A slot that arrives in the same tick its run is aborted, or its agent is skipped, goes straight back undispatched. A pause while queued hands the slots and the run's own permit back when the slots arrive, and the agent takes both again on resume. A released slot passes straight to the oldest waiter.
