# C001 — Blocking resume of a running agent corrupts the live run and loses its result

- **Claim:** C001 (source AGENTS-001, agents family) · **Axis/grade:** LX / ESTABLISHED
- **Pin:** ce180d82 (worktree `pin-ce180d82`), graded 2026-11-11

## Defect
A blocking resume of an agent that is still running — `Agent({resume:<id>, run_in_background:false})` — is not refused. It returns pi's internal error text as a success-shaped reply, flips the live agent's record to `status:"error"` (`hasRunning()` goes false, `steer_subagent` refuses, stop/abortAll skip it), and a follow-up `get_subagent_result` marks the record consumed, so the real answer that lands seconds later is never notified. The default (background) resume path guards exactly this case; the foreground path does not.

## Reproduction
```
cd probes/agents && ./RUN.sh p05-resume-and-mention.probe.test.ts -t R1
# -> out/p05-r1-blocking-resume-of-running-agent.json
```
Observed sequence (original run still in flight):
1. Reply: `Agent failed: Agent is already processing. Specify streamingBehavior ('steer' or 'followUp') to queue the message.` — with `isError` unset (success-shaped).
2. Record immediately after: `{status:"error", completedAt:true}`; `manager.hasRunning()` = false.
3. `steer_subagent` -> `Agent "…" is not running (status: error). Cannot steer a non-running agent.`
4. `get_subagent_result` -> `Status: error … Error: Agent is already processing…` (marks result consumed).
5. 3.5 s later the record is `{status:"completed", result:"CHILD_FINAL_ANSWER", error:<stale text>, resultConsumed:true}` and the parent received **zero** subagent-notification messages.

Code anchors: the running/queued refusal exists only inside `if (runInBackground)` (src/index.ts:2132-2144); the foreground branch calls `manager.resume` directly (src/index.ts:2168 -> src/agent-manager.ts:1190-1231); `abort()`/`abortAll()` act only on `status === "running"` (src/agent-manager.ts:1442, :1543). SUPPORTED (code-read, not reproduced): the failed resume also aborts the live run's nested children (src/agent-manager.ts:1229) and the nested Agent tool has the same unguarded call (src/nested-tools.ts:189). Guarded contrast: `out/p13-background-resume-refusal.json`.

## Cost
Orchestrating LLM and operator. Backgrounds are the default, so the agent a model wants to "resume and wait for" is usually still running; each such call leaves a live run that cannot be steered or stopped and whose result can be lost.

## Cure options
1. **Primary (investigator):** hoist the running/queued refusal (src/index.ts:2139-2144) above the `runInBackground` branch, and make `AgentManager.resume()` itself refuse running/queued records so the foreground path and the nested Agent tool (src/nested-tools.ts:189) are both covered.
2. Alternative: on a foreground resume of a running agent, queue the message as a followUp steer (the behaviour the current error text already tells the model to ask for) instead of refusing.
3. Minimum harm reduction: never flip the live record to `error` from a refused resume, and mark the refusal `isError:true` so the model does not read it as a result.
