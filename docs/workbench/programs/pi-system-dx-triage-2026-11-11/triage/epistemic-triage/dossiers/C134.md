# C134 — A Pi restart kills every workflow run id while its journal sits on disk

- **Claim:** C134 (source JOURNAL-001, journal family) · **Axis/grade:** gap / ESTABLISHED
- **Pin:** ce180d82 (worktree `pin-ce180d82`), graded 2026-11-11

## Defect
A Pi restart kills every workflow run id although the run's journal and script are still on disk in the same session task dir: `resumeFromRunId`, `workflow_reconcile` and `workflow_observe` all refuse, session_start announces nothing, and the only advice given (run without `resumeFromRunId`) repeats an effect whose dispatched marker is sitting unread in that journal.

## Reproduction
```
PIN=.../pin-ce180d82  PJ=.../probes/journal
cd $PIN && ./node_modules/.bin/vitest run --config $PJ/vitest.probe.config.mts $PJ/p01-restart.probe.ts   # -> out/p01-restart.json
cd $PIN && ./node_modules/.bin/vitest run --config $PJ/vitest.probe.config.mts $PJ/p01b-restart-duplicate.probe.ts  # -> out/p01b-restart-duplicate.json
```
Observed: `journalOnDisk true, scriptOnDisk true`, journal row `{kind:node, capabilityId:furnace.run.start, effectClass:external, dispatched:true}`; after session_shutdown + a fresh extension instance in the SAME cwd and session id: resume -> `No workflow run "wf_0f20f5d9befd" in this session. Nothing has run yet — call this without resumeFromRunId.`; `workflow_reconcile` inspect is byte-identical to a never-existing id (`inspectEqualsUnknown true`); session_start notifies nothing. In p01b the same-process marker correctly refuses the resume (effectInvocations stays 1), but after restart the advised fresh run re-runs the effect (effectInvocations 2, `markerStillOnDisk true`, no mention of the earlier dispatch).

Code anchors: run map is process memory (src/index.ts:2460 `workflowTasks`; :1254-1255 cleared at session_shutdown; src/workflow/task.ts:313-334 `resolveResumeTarget` reads only that map); session_start (src/index.ts:929-992) scans nothing. Documented as a limit (docs/workflows.md:116 "Restart pi and the run id is dead") **against** docs/workbench/08-lifecycle-and-recovery.md:56 ("Kill after Furnace side effect before returned Run ID ... Required outcomes: reconciliation/uncertainty/conflict; no duplicate effects") and src/workflow/journal.ts:57-64 (the marker exists for "a run killed between a provider's side effect and its result").

**Caveat (from the investigator):** the effectful capability in p01b is a probe-only stand-in (effectful-mock.ts); no shipped capability is effectful today (C145 / JOURNAL-012), so the duplicate-effect exposure is latent while the dead-run-id behaviour is current.

## Cost
Every operator or agent whose Pi exits, crashes, is /reload-ed or restarted while or after a workflow ran: all replay value of that session's journals is lost (full re-pay of every agent), and the dispatch tripwire protects only kills that leave the Pi process alive.

## Cure options
1. **Primary (investigator):** in `resolveResumeTarget` fall back to `<sessionTaskDir>/<runId>.workflow.jsonl` + `.workflow.js` when the id is not in memory (both files already exist there); at session_start list journals in the session task dir whose last node row is an unsettled dispatched marker and notify with the run id, capability and position.
2. Alternative: a `workflow_reconcile` action that takes an explicit journal path, so recovery is possible without changing resume semantics.
3. Honesty stopgap: when a journal file exists for the refused id, the refusal must say so and must not advise a fresh run while an unsettled dispatched marker exists.
