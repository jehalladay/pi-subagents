# C248 — Schedules beyond ~24.8 days fire immediately, intervals become a spawn loop

- **Claim:** C248 (source SCHEDULING-001, scheduling family) · **Axis/grade:** missing-req / ESTABLISHED
- **Pin:** ce180d82 (worktree `pin-ce180d82`), graded 2026-11-11

## Defect
Interval and relative schedules have no upper bound: any value above Node's 2^31-1 ms timer ceiling (~24.8 days, e.g. `30d` or `+30d`) fires immediately and, for intervals, every ~1 ms with `bypassQueue:true` — a runaway spawn loop instead of a monthly job.

## Reproduction
probes/scheduling/bounds.probe.ts B1-B3 (vitest; output probes/scheduling/bounds.probe.out.txt):
- `parseInterval('30d')` = 2,592,000,000 ms (> 2,147,483,647);
- `addJob('30d')` -> `TimeoutOverflowWarning: 2592000000 does not fit into a 32-bit signed integer. Timeout duration was set to 1.` and **31 manager.spawn calls within 60 ms**;
- `addJob('+30d')` -> spawn after ~1 ms, job auto-disabled;
- `detectSchedule('+99999999999d')` throws `RangeError: Invalid time value`.

Code anchors: src/schedule.ts:174 `setInterval(..., job.intervalMs)`, :180 `setTimeout(..., delay)`, :381-385 `parseInterval` accepts `\d+`; spawns bypass maxConcurrent via schedule.ts:254 `bypassQueue:true`. README.md:95-96 documents `2d` and no maximum (`grep -ci '24 days|2147483647|maximum interval' README.md` = 0).

## Cost
Any user who asks for a monthly/quarterly schedule: a scheduled job spawning real LLM agents every millisecond, bypassing maxConcurrent — a cost/rate-limit incident; the reply even reports `Next run: <30 days ahead>` while it is already firing.

## Cure options
1. **Primary (investigator):** in `detectSchedule` reject intervalMs/delay > 2,147,483,647 (and absurd relatives) with a message naming the ~24.8-day ceiling; state the bound in README "Schedule formats" and in the `schedule` param description.
2. Alternative: chain `setTimeout` segments for long delays/intervals so long schedules actually work instead of being refused.
3. Defense in depth: scheduled spawns should not set `bypassQueue:true`, so even a mis-armed timer cannot exceed maxConcurrent.
