# C252 — A corrupt schedule file silently destroys the user's jobs

- **Claim:** C252 (source SCHEDULING-005, scheduling family) · **Axis/grade:** DX / ESTABLISHED
- **Pin:** ce180d82 (worktree `pin-ce180d82`), graded 2026-11-11

## Defect
A corrupt schedule file is silently treated as empty and the next mutation rewrites it, destroying the user's jobs with no diagnostic and no backup (the behaviour is pinned as "self-heals" by a test).

## Reproduction
probes/scheduling/store-nextrun.probe.ts S2: two persisted jobs, file truncated by 20 bytes ->
- `reloaded.list().length = 0`, `console.warn = 0`, `console.error = 0`;
- after one add, the file holds only `['new']`; no `.bak`/`.corrupt` sibling exists.

Code anchors: src/schedule-store.ts:74-81 `load()` — `catch { /* corrupt — start fresh, next save rewrites */ }`; test/schedule-store.test.ts:105 pins it: "self-heals from a corrupt JSON file — load silently empties, next save rewrites".

## Cost
A half-written file (disk full, editor mishap, interrupted rename on a network FS) erases a user's recurring jobs the next time any job is touched; nothing tells them.

## Cure options
1. **Primary (investigator):** on parse failure: `console.warn` naming the path, rename the file to `<name>.corrupt-<ts>` before the first save, and surface a toast at scheduler start.
2. Alternative: refuse mutations while the store is unreadable (load error state), so recovery is possible before anything rewrites.
3. Update test/schedule-store.test.ts:105 to assert preservation + diagnostic instead of pinning the destructive behaviour.

C265 (SCHEDULING-018) preserves the adjacent good behaviour (atomic temp+rename writes, stale-PID lock recovery) — the cure must not regress those.
