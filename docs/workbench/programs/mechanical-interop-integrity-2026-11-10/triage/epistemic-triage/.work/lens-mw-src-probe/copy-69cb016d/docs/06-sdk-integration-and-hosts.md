# 06 — SDK integration and execution hosts

## General rule

Use **public native SDKs directly** from the application's composition root. Add a local mapping only where data/semantics actually cross product boundaries. Provider-specific tool presentation stays at the provider edge. No universal `asTools`, no duplicate lifecycle engines.

## Forge adapter (target)

Use public Forge SDK session and typed operations; do not spawn `forge` per gate if supported resident SDK is available. Preserve: operation ID, actual candidate source/basis, status, all verdict axes, reason codes, partial/unknown, replay/cache distinctions, artifact/evidence refs. Only map to application `VerificationResult` after proving the mapped verdict; retain the original result for diagnosis.

Forge is independently evolving Workspace Families and an optional host cache. Their specifications currently label these features unimplemented. Do not invent `workspace.child()` or claim cache-based PASS until a real SDK/release ships.

## HyperUnix adapter (target)

Use HXQ/named queries through the public SDK, not CLI text parsing. Preserve coverage, bounds, truthful `known_empty` versus incomplete, query/basis identity and evidence. Query result reuse across source mutation requires explicit freshness check.

## ReactiveFiber compiler (target)

An adapter needs actual context text, input/definition/model capability basis, render/transaction reference, budget/necessity outcomes and error distinction. If RF exposes only Python/CLI access at the relevant implementation revision, record process cost and typed protocol need. Never silently replace mandatory RF with static strings outside a separately named fixture mode.

## Agent provider (target)

An agent workflow may use Claude, OpenAI, Pi, or other SDK directly; no portability requirement. Forge already separates provider-neutral tool catalog/invocation machinery from specific Claude and Codex integrations. Consume the selected adapter. Do not expose every SDK method automatically. Restrict roles and retain tool-call identity/correlation.

## Furnace executor host (target)

The shipped TypeScript executor SDK provides `ExecutorApp`, `ExecutionContext` and `ExecutionResult`. Implement an app-specific adapter:

```ts
// Future adapter sketch; not committed runtime integration:
const app = new ExecutorApp();
app.executor("development", async ctx => {
  const request = decodeFromFurnace(ctx);
  const owned = await createHostOwnedClients(ctx);
  try {
    const result = await develop(owned.services, request);
    return projectIntoFurnaceExecutionResult(result);
  } finally {
    await owned.close();
  }
});
```

The adapter must explicitly map `verified_candidate`, `verification_failed`, `needs_evidence`, `indeterminate` into Furnace's success/failure/cancelled/indeterminate semantics as appropriate to its Work policy. **An application domain failure is not automatically an SDK transport error.** The adapter may depend on both Furnace SDK and the workflow library; neither core depends on the other.

Furnace owns admission, retries, Work/Attempt lifecycle, recovery, supervisor intents and observations. The app may directly call Furnace when appropriate but must not implement a parallel scheduler.

## Host separation

- Local host: ordinary CLI invocation, caller or host owned dependencies, no durability claim.
- Furnace host: Furnace executor callback; native Work/Attempt identity; no magical replay of program locals.
- Remote cloud worker: future separate adapter; host-managed artifact, image, credentials, materialization and invocation lifecycle.
- Agent tool: future provider-specific adapter; tool invocation transport/flags do not replace domain verdict.

## Upstream feedback

Each integration failure must name the SDK surface/version, smallest reproducer, precise unsupported behavior, affected workflow, workaround if any, and proposed product owner. Prefer improving the owning product over maintaining permanent MechanicalWorkflows glue.

### Host-provided cancellation: pre-dispatch barrier and post-dispatch typed uncertainty (PIWB-MW2-R001, PIWB-MW2-R002)

`AgentOptions.signal` and `LiveDevelopmentOptions.signal` accept a host `AbortSignal`. A signal already aborted before the first provider side effect makes `developLive` (at entry and again before the agent runner) and `runClaudeImplementation` (before the SDK module load) refuse with `DEVELOPMENT_CANCELLED_BEFORE_DISPATCH`, a class distinct from `AGENT_OUTCOME_NOT_ESTABLISHED` and from RF or Forge refusals. Nothing is dispatched, written, committed or gated, and the refusal claims no rollback. While a session runs, `runClaudeImplementation` forwards the signal into the SDK through the SDK's public `options.abortController` (EAT-R014; the key is present only when the host supplied a signal, is absent from the replay-identity configuration, and its listener is removed once the run settles). The stream also stops, and the run surfaces as `AGENT_ABORTED_DURING_RUN` carrying the last seen session id; an abort never relabels as rollback. `sdkAbortControlSupport` (`sdk-abort-support.ts`) reads the resolved SDK version and its shipped declarations and reports whether `options.abortController` exists; the live abort test skips with that reason when it does not, and `replay.sdk` records the resolved version on every completed run.

An abort observed AFTER the first provider side effect (PIWB-MW2-R002) makes `developLive` refuse with `DevelopmentAbortedAfterDispatchError` (`DEVELOPMENT_ABORTED_AFTER_DISPATCH`), whose `uncertainty` field (`UNCERTAIN_AFTER_ABORT`, `apps/development-rig/src/post-dispatch-abort.ts`) records the worktree path, base and current HEAD, the native agent session id when one is known (null otherwise, never fabricated), the Forge operation id when a gate observation named one, and a `phase`: `during-agent-edits` (uncommitted files stay on disk and are listed in `dirtyPaths`), `committed-not-gated` (the agent's commit exists and no Forge request, and no reviewer call, is dispatched after the abort), or `after-forge-dispatch` (at most one gate request may have been dispatched, since the refusal can precede the request when a clean-basis check or initialize fails; the operation id is preserved when one was named and the observation is not credited). `agentIgnoredAbort` is true only when the host saw the signal already aborted at the moment the agent returned control (the agent ran to completion despite a requested cancellation that was visible); an abort that arrives after the agent returned, such as one during review or the Forge request, reports false, and an abort whose arrival the host cannot order before the agent's return is never labelled ignored. The host never rolls back, cleans, resets, re-runs the agent or re-dispatches Forge: `rollback` is always `not-attempted` and `reconciliationRequired` is always true. `runClaudeImplementation` stops reading the SDK stream when the signal aborts and throws `AGENT_ABORTED_DURING_RUN` carrying the last session id seen on the stream. Cross-host SubjectBasis extension (candidate commit and tree, gate manifest digest, instruction and skill configuration in replay identity) stays out of scope.

A lost acknowledgement WITHOUT an abort (EAT-R045, EAT-R136, EAT-R163) settles as typed uncertainty as well. `developLive` refuses with `DevelopmentLostAcknowledgementError` (`DEVELOPMENT_LOST_ACKNOWLEDGEMENT`, `apps/development-rig/src/effect-reconciliation.ts`), whose `uncertainty` field (`UNCERTAIN_AFTER_LOST_ACK`) carries the same native fields as the abort record (worktree, base and HEAD, session id or null, Forge operation id or null, `dirtyPaths`, `rollback: not-attempted`, `reconciliationRequired: true`) plus `effect`: `writer` when the agent runner threw after an observable side effect (HEAD moved past the base, or `git status` lists dirty paths, or Git could not be read; an agent that threw and left no trace keeps its own refusal), or `gate` when the `gate.run` request was dispatched and its response never arrived (`FORGE_DISPATCH_OUTCOME_UNKNOWN`; a Forge connection that fails before any request keeps its own refusal). The host runs the agent at most once and dispatches Forge at most once; nothing retries. `reconcileUncertainEffect(record, { git, forgeOperation? })` is the one pure decision point: it reads the injected native sources, executes no effect and returns `{ effect, disposition: occurred | not-occurred | unknown, retryPermitted, evidence }`. `retryPermitted` is true only when `disposition` is `not-occurred` and `evidence` names the native record consulted (for a writer: HEAD at the base with a clean worktree; for a gate: an authoritative `{ found: false, id }` Forge lookup); an unavailable or inconclusive source yields `unknown` with no permission. The claim effect kind stays pinned by `beads-claim.test.ts` (a lost claim acknowledgement never triggers a second update). Nothing consumes the decision yet: the typed cached-answer reuse refusal of EAT-R049 and durable persistence (EAT-R050, EAT-R051) stay separate work.

### Structured progress callback and stage mapping (EAT-R015)

`LiveDevelopmentOptions.onProgress` (`apps/development-rig/src/progress-stages.ts`) receives one `ProgressEvent` per lifecycle stage, in this order and no other: `discovery`, `context`, `sdk_startup`, `first_edit`, `commit`, `gate_dispatch`, `settlement`. Each event carries `stage`, `rigStage` (the receipt stage it reports under), a non-null `disposition` and the latest native `refs` (base commit, RF render id, agent session id, candidate commit and tree, Forge operation id; null until observed, never fabricated). `disposition` reads `none` while nothing was dispatched that could write (discovery, context), `uncertain` from the writer dispatch until the gate answers for the committed candidate, and `settled` only at `settlement` when the gate passed or failed that exact commit. `first_edit` also names `observedVia`: `agent-stream` when `runClaudeImplementation` saw an Edit or Write tool use on the SDK stream (through `AgentOptions.onFirstEdit`, which never reaches the SDK query options; a caller-supplied `onFirstEdit` on `LiveDevelopmentOptions` is chained after the host event, fires once, on the first stream edit that `runClaudeImplementation` sees, and cannot fail the run whether it throws or returns a rejecting promise), `host-git-diff` when the stream reported none and the host found the edit in the committed change. A run that refuses emits only the stages it reached, so `settlement` appears on completed runs only. The callback observes: one that throws or rejects changes no outcome. The program names its stages differently from the receipt (the program 03 vocabulary discover/context/agent/commit/Forge/settled is a target, not what the receipt emits), so the mapping below is committed and `apps/development-rig/test/progress-callback.test.ts` fails when the table and `STAGE_MAP` differ, when the receipt gains or loses a stage, or when `live-development.ts` emits a stage outside the vocabulary.

| Program stage | Receipt stage | Emitted when |
| --- | --- | --- |
| `discovery` | `discovery` | the Git tracked-file census completed on the clean basis |
| `context` | `context` | the task context (plain or RF render) was compiled |
| `sdk_startup` | `agent` | the writer is about to dispatch, after the effect-intent record when one is configured |
| `first_edit` | `agent` | the first Edit or Write tool use, or the committed source change when the stream reported none |
| `commit` | `candidate` | the agent's commit passed the basis, manifest and source-change checks |
| `gate_dispatch` | `verification` | immediately before the single Forge gate request |
| `settlement` | `verification` | the run completed and the intent record, when present, was settled |

### Invocation effect-identity record (EAT-R048, EAT-R049 degenerate form)

`developLive` returns `invocation` (`apps/development-rig/src/invocation-identity.ts`, schema `mechanical.invocation-identity/v1`) whenever the agent runner reports a `replay` identity; an injected `AgentRun` that omits `replay` leaves `invocation` absent and the host fabricates none. The record names six axes: `source` (the clean Git commit and tree observed before the agent dispatched), `sdk` (`{name, version}` read from the installed `@anthropic-ai/claude-agent-sdk` manifest bytes at load time, never a literal; `null` and `complete:false` with `missingAxes:["sdk"]` when no manifest is readable, and `CLAUDE_AGENT_SDK_MANIFEST_INVALID` before any dispatch when a manifest names no such package, no version, or a version that is not a semantic version (EAT-R032)), `prompt` (`promptSha256`), `settings` (`settingsSha256`, the SHA-256 of the canonical serialization of the effective configuration: sorted keys, no whitespace, no path, time or locale input), `gateManifest` (`gateManifestSha256`) and `skills` (the host-named `LiveDevelopmentOptions.skillFiles`, relative repo paths hashed at the clean basis before any dispatch and recorded in the host's order; the default enumeration is empty and an unreadable, duplicate or out-of-root name refuses with `INVOCATION_IDENTITY_SKILL_UNREADABLE`, `INVOCATION_IDENTITY_SKILL_DUPLICATE` or `INVOCATION_IDENTITY_SKILL_PATH_INVALID`). Each axis carries its own SHA-256 in `axes`, and `identitySha256` hashes the canonical preimage `{schema, axes}`, so `differingAxes` names the axis a one-byte change touched and `verifyInvocationIdentity` recomputes every recorded digest from the recorded inputs. The host ships no answer cache; the degenerate EAT-R049 form is a structure guard (`test/invocation-identity.test.ts`) that no module under `apps/development-rig/src` keys a cache or reuse decision on a proper subset of the axes. The typed reuse refusal waits for the EAT-R045 reconcile decision point, and persistence beyond the CLI's stdout JSON (EAT-R050, EAT-R051) stays a Seat question. This is app-local replay evidence inside `@mechanical/development-rig`, not a cross-host replay authority.

#### Cross-host axes and the effect-intent record (EAT-R012, EAT-R013; MechanicalWorkflows-loexn.7)

The record carries nine further axes beside the six above: `workspace` (the canonical realpath `developLive` observes), `task` (SHA-256 of the task text it observes), `gateParameters` (the `gate.run` request it sends, overridable by the host), and six the host must state through `LiveDevelopmentOptions.hostIdentity`: `principal` (principal and session), `piInvocation` (the Pi invocation id), `descriptor` and `tarball` (SHA-256 digests), `contextProfile` and `evidenceProfile`. Model, tools and permission mode ride in `settings`; provider and SDK name and version ride in `sdk`. An axis the host does not state is `null`, listed in `missingAxes`, and hashes differently from any stated value; the host never fills it. `assertReplayable(record)` recomputes the missing set from the recorded inputs and throws `InvocationReplayRefusedError` (`INVOCATION_REPLAY_AXIS_MISSING`, `axes` naming each) so a forged `complete` flag does not help, and `requireReplay: true` applies the same check to the host axes before any dispatch. Index-only, untracked, symlink and submodule changes in the source tree never reach a write: `cleanGitBasis` refuses them with `WORKSPACE_NOT_CLEAN` at preflight and at every barrier.

`LiveDevelopmentOptions.effectIntent` (an `EffectIntentStore`; `fileEffectIntentStore(path)` is the atomic single-file implementation and `readEffectIntent(path)` its reader) turns on the durable record (`src/effect-intent.ts`, schema `mechanical.effect-intent/v1`). `developLive` persists exactly one intent, disposition `uncertain`, immediately before the writer dispatches; a failed write refuses with `EFFECT_INTENT_NOT_RECORDED` and the writer never runs. It then attaches the native agent session, the candidate commit and tree, and the Forge operation id as each is observed (a failed update after dispatch surfaces as `EFFECT_INTENT_UPDATE_FAILED`; a different ref over one already held is `EFFECT_INTENT_REF_CONFLICT`). `settleEffectIntent` marks the record `settled` only when the gate verified exactly the candidate tree under the recorded gate-definition hash with a native Forge operation id; a lost acknowledgement, an unknown verdict or any mismatch leaves it `uncertain` with the refs kept. `parseEffectIntent` refuses a settled record that does not bind the committed tree, the gate definition hash and an operation id (`EFFECT_INTENT_INVALID`). Limits: the host learns the candidate commit when the agent returns, so a process killed inside the agent run reads `uncertain` with no commit; the `disposable-child-crash-harness` gate is not run (the test kills a child process with SIGKILL after the commit is attached); the CLI does not yet pass a store; and the record is app-local, not a Pi-side join key beyond the stated `piInvocation` axis.

A settled record holds exactly one settlement (EAT-R016; MechanicalWorkflows-loexn.8 slice 5): `settleEffectIntent` on a record already `settled` returns that same record when the completion repeats the recorded verdict and Forge operation, leaves it untouched when a late observation could not settle it (unknown verdict, other tree or gate definition, no operation id) unless that observation names a different Forge operation, which refuses with `EFFECT_INTENT_REF_CONFLICT` as an unsettled record does, and refuses with `EFFECT_INTENT_SETTLEMENT_CONFLICT` when a different verdict or operation arrives for the same candidate, so a twice-delivered or contradictory completion event never writes a second settlement.

## Native HX and RF adapter cuts (2026-10-15)

`apps/development-rig/src/hx-scope.ts` consumes a public HyperUnix TypeScript SDK result, retaining incomplete coverage and requiring a task-scoped, revision-pinned query digest before returning a complete `ScopeResult`. The installed `find` answer on a real package is explicitly `unknown`, because its coverage is incomplete, its subject is a filesystem census, and no task query was proven. A bounded source dependency read retained known positive rows with incomplete coverage; a broad read hit `SDK_PROTOCOL_LIMIT`, which the adapter maps to unknown rather than success. `apps/development-rig/src/rf-context.ts` invokes the installed `rf context render --strict --json` leaf, retains native render/budget/graph identities, and refuses the observed starter placeholder. A real RF render occurred, but useful task-grounded producer content and native HX task scope are not established, so neither adapter is silently substituted for the current Git/plain-context live journey. The adapter resolves the rf executable through `MECHANICAL_RF_BINARY` (else a bare-name PATH lookup) exactly as `rf-provision.ts` does, via the shared `rf-binary.ts`. Failure is structured: a producer that exits nonzero yields `RF_RENDER_UNESTABLISHED` carrying the real `exitCode` and, when its stdout held a refusal envelope, the first `diagnosticCode` (for example `RF_WORKSPACE_INVALID` at exit 3); an rf that cannot be started at all yields the distinct `RF_UNAVAILABLE`, and no failure path simulates a render. Every render also runs under one `rf --idempotency-key` (supplied through `RenderOptions.idempotencyKey` or minted per call; `developLive` mints one per invocation and accepts `renderIdempotencyKey` so a host retry of the whole journey replays rather than re-commits). A reply lost after a possible commit (timeout, `maxBuffer`, signal kill, other spawn failure; `Result.transport` set by the default executor) is re-issued under the same key up to `maxReissues` times (default 1), never under a fresh key; when the budget runs out the failure is `RF_TRANSPORT_UNACKNOWLEDGED` naming the key. A domain refusal (for example `RF_IDEMPOTENCY_KEY_CONFLICT` at exit 4) and `RF_UNAVAILABLE` are never re-issued. The projection carries `idempotencyKey`, `acknowledgement` (`committed`, or `replayed` when the reply holds `result.replay_of_operation_id`) and `replayOfOperationId`; a replayed reply passes the same task, revision, model and budget checks. A truncated stdout at exit 0 stays `RF_RENDER_UNESTABLISHED: malformed JSON envelope` (pinned by an existing case), not a transport failure.

`renderTaskContext` (`apps/development-rig/src/rf-context.ts`) hands workers a typed `RfContext` that adds the RF workspace id (`result.workspace_id`), the explicit `--actor` the render recorded, and rf CLI version plus SDK versions (a second `rf --json --version` call through the same injected executor) to the render id, model, graph revision and digest. It projects text and identities only; a missing or non-`rfw_` workspace id, a blank or mismatched actor, or a malformed or unsuccessful version envelope refuses with an `RF_CONTEXT_` prefixed error (MechanicalWorkflows-g00df).

## Pi Workbench host binding program (2026-11-04)

See the [coordinated audit and design](programs/pi-workbench-interop-2026-11-04/README.md) before implementing a Pi consumer. The host must supply app-specific `discover/compileContext/implement/verify` closures, native source basis and effect authority; a Pi `hyperunix.find` result or RF preview is not automatically a Mechanical complete task scope or committed render. `workflow_execute` is the proposed async function launch surface, while Furnace retains native durable Run/Attempt supervision. The program records no new conformance evidence and does not relax provider-neutral packaging or existing application authorization.

`renderTaskContext` can reuse a recorded render: with `RenderOptions.sessionId` it reads `rf context history` for that session, confirms a candidate with `rf context explain` (task digest equal to the SHA-256 of the exact task and revision bytes, same model, exact replayability) and reads it back with `rf context show` under the same grounding checks, reporting `source` `reused` or `rendered`. `developLive` hands a second worker the render id and session id (`contextHandoff`), and `resolveRenderHandoff` resolves them through `context show`. Injected-executor evidence only; see `docs/10-current-state-and-gaps.md`.

The review-session receipt names its SDK (EAT-R032 b1; MechanicalWorkflows-loexn.19): `runClaudeReview` in `apps/development-rig/src/claude-review.ts` resolves the installed `@anthropic-ai/claude-agent-sdk` manifest with the same two-step lookup `runClaudeImplementation` uses (exports-map `package.json`, then a walk up from the main entry) and records `sdk: {name, version}` beside the `review-session` evidence on every approved or rejected result. A manifest that names another package or carries a non-semver version refuses with `CLAUDE_AGENT_SDK_MANIFEST_INVALID` before `query()` runs; a manifest that cannot be located records `sdk: null` rather than a guessed version, and an `unknown` verdict carries neither evidence nor `sdk`. The receipt also carries the implementation class's incompleteness marker: `complete: false` with `missingAxes: ["sdk"]` when `sdk` is null, `complete: true` with `missingAxes: []` when a manifest resolved (MechanicalWorkflows-mwlr9); the default manifest reader binding is pinned by a source-structure guard in `apps/development-rig/test/claude-review.test.ts`.
