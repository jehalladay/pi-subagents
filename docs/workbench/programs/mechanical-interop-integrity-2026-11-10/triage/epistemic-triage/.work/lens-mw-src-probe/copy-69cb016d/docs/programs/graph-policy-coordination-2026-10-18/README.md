## Ownership and decision pipeline

MechanicalWorkflows retains pure `Policy<O,I,M>.propose`, typed intents, `reconcile`, fixtures and the `mw.training-export.v1` export (a per-decision sidecar is TARGET, cf. APO-009; none exists at HEAD 19ca8d4). GraphPolicyCLI's program specifies (design-only; no implementation claimed as of 2026-10-18) typed graph-function scoring over basis-pinned (at HEAD 19ca8d4 only the git basis and landing candidates carry stable ids and revisions; Beads issues carry an id but no per-task revision; agents, resources and artifacts have no identity/revision model in MechanicalWorkflows) agent/task/resource/artifact/capability observations. It has no native effects, task truth, CAS authority or new central workflow runner.

Host: obtain bounded typed graph and **pre-sampling** legal candidates → GP is specified to score keyed agent/task pairs → a named selector samples with actual behavior log probability or selects deterministic proposal (TARGET: at HEAD 19ca8d4 the only `Selector<O>` chooses "left"|"right" and every exported decision carries `logProb: "unknown"`; no channel records a behavior log probability) → host maps symbolic choice into typed Intent whose `expectedRevision` is the batch `Basis.revision` (per-entity source revisions are TARGET) → MechanicalWorkflows reconcile enforces conflicts, protected scopes, limits and staleness → native executor runs accepted action → verifiers report actual outcome (today: seeded gate draw / tape digest in fixture and replay episodes and the single live `gate.run` flow; a general live verifier channel and an episode schema slot are TARGET).

Independent pair logits do not guarantee a globally capacity-feasible assignment. For a multi-task assignment choose either a capacity-aware deterministic matching resolver or a documented joint/autoregressive sampler recording *joint* behavior probability; both options are TARGET components (no capacity-aware matching resolver exists today).
